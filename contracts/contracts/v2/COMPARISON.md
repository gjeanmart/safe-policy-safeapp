# Policy Engine V1 vs V2 rev 3: what changes, proven on-chain

Each row runs the same scenario on two real Safes 1.5.0 from the same infrastructure: one guarded by the vendored V1
`SafePolicyGuard` (71b9cb0), one by the rev 3 engine (`PolicyGuard` + `PolicyGuardConfig`) with its policies. Source:
`test/v2/compare/V1vsV2.test.ts`; each test is named `<scenario>: V1 <outcome>, V2 <outcome>`.

V1 policies used: the vendored `ERC20TransferPolicy`, the repo's `SpendingLimitPolicy`, and
`contracts/v2/test/E2eV1Policies.sol`: 8ee68a8's `AllowPolicy` / `DenyPolicy`, a port of 8ee68a8's `CoSignerPolicy`
(`ModulePathUnsupported` on modules, as 8ee68a8's `SafenetPolicy`), and a stand-in timelock (neither V1 commit has one;
it behaves as the "fallback timelock" of WA-4014).

| Design doc row                             | Scenario                                                                      | V1                                                                        | V2 rev 3                                                                                            | Test (`V1 vs V2 rev 3 …`)                                                                                                                |

| §1.1                                       | Same, with an exact Allow for `addOwnerWithThreshold`                         | The attacker is added as owner at once                                    | Delayed: `NotScheduled`                                                                             | `addOwnerWithThreshold under an exact Allow rule: V1 executes at once, V2 delayed (NotScheduled)`                                        |
| §1.1 (control)                             | A payment with no rule of its own                                             | Delayed (fallback timelock `NotScheduled`)                                | Delayed (`NotScheduled`)                                                                            | `a payment with no rule of its own: V1 delayed (fallback timelock), V2 delayed (NotScheduled)`                                           |
| §1.1 configuration                         | Change the engine configuration                                               | Waits the engine's own DELAY (`RootConfigurationPending`)                 | `configure` is an owner transaction: it waits the same Timelock (`NotScheduled`)                    | `engine configuration under the owners timelock: V1 waits its own DELAY, V2 waits the same Timelock (NotScheduled)`                      |
| §1.2 one rule table for every caller       | A USDC payment allowlist; the recovery module calls `swapOwner`               | Denied: `AccessDenied` (no rule for `swapOwner`, no fallback)             | Executes after recovery's 72h Timelock                                                              | `recovery's swapOwner next to a payment allowlist: V1 denied (AccessDenied), V2 executes after R`                                        |
| §1.2                                       | Grant `swapOwner` to the recovery module                                      | The rule grants every module: Ops replaces an owner with the attacker     | Only recovery: Ops gets `NotGranted`                                                                | `granting recovery's swapOwner: V1 grants every module (ops swaps owners), V2 only recovery (NotGranted)`                                |
| §1.3 a co-signer only on the multisig path | A global co-signer; the recovery module's `swapOwner`                         | `ModulePathUnsupported`: every module is bricked, recovery included       | `MissingApprovals`, then executes once the co-signer `approve`s on-chain                            | `a global co-signer and a module transaction: V1 reverts (ModulePathUnsupported), V2 executes with an on-chain approval`                 |
| §1.4 a freeze cannot cover configuration   | Everything denied; a malicious configuration was requested                    | Applied after DELAY (configuration skips every policy), then drained      | The guardian freezes the owners' Timelock: the scheduled `configure` is `AttachmentFrozen`          | `a pending malicious configuration under a deny-everything fallback: V1 applies it (drain), V2 blocked by the freeze (AttachmentFrozen)` |
| §1.4 configuration delayed both ways       | Stop the Safe now                                                             | A new Deny rule waits DELAY (`RootConfigurationPending`); payments go out | The guardian freezes at once (Timelock delay 0 is a kill switch): `AttachmentFrozen`                | `stopping the Safe: V1 a new deny rule waits DELAY (RootConfigurationPending), V2 the guardian freezes at once`                          |
| §1.5 the guard conflicts with modules      | Owners' USDC allowlist (vendor A); a spending module pays its own payee (B)   | Denied (`Unauthorized`): the owners' allowlist overrides the module       | Executes: Ops has its own Args recipients and Limit                                                 | `a spending module paying its own payee next to the owners' allowlist: V1 denied, V2 executes (per actor)`                               |
| §1.6 limits only cover transfers           | 5,000 USDC a month; `approve(attacker, 100,000)`                              | Executes; the attacker pulls 100,000                                      | `LimitExceeded` (an approval costs its full amount)                                                 | `approve(attacker, 100,000) under a 5,000 limit: V1 executes (unlimited allowance), V2 LimitExceeded (full amount priced)`               |
| §1.6                                       | Same; send 10 ETH                                                             | Executes                                                                  | `LimitExceeded` (native value always counted)                                                       | `10 ETH sent under a token limit: V1 executes, V2 LimitExceeded (native value counted)`                                                  |
| §4 batches                                 | Transfer limit + an Allow on MultiSend; a batch of two 50,000 transfers       | Executes: 71b9cb0 does not look inside a batch; the Safe is drained       | `LimitExceeded` (every sub-call is checked, summed over the batch)                                  | `transfers inside a MultiSend: V1 (71b9cb0) lets an allowed batch through unchecked, V2 checks every sub-call (LimitExceeded)`           |
| ERC-1271 (rev 3 decision 12)               | Owners sign a USDC permit off-chain                                           | Drained: the fallback handler validates it, no guard call                 | Refused (`InvalidSignature`): the install sets Safe's `TokenCallbackHandler`, which has no ERC-1271 | `an off-chain owner signature on a permit: V1 drained, V2 refused (its install sets TokenCallbackHandler, no ERC-1271)`                  |
| Gap kept (opt-out)                         | Same, V2 installed keeping the `CompatibilityFallbackHandler`                 | Drained                                                                   | Drained too: off-chain owner signatures bypass every policy                                         | `the documented gap: V2 installed keeping the CompatibilityFallbackHandler is drained by the same permit`                                |

Changed from the rev 2 table: the ERC-1271 row. Rev 2's `PolicyFallbackHandler` answered `0xffffffff`; rev 3 removed
that handler and its install sets Safe's own `TokenCallbackHandler` instead (token callbacks, no ERC-1271). The last row
keeps the gap visible for owners who opt out and keep an ERC-1271 handler (the app warns them).
Not testable on-chain: the §1.5 half about Safe's AllowanceModule (not vendored; approximated by a module with its own
payee above), and the UI / indexer rows.
